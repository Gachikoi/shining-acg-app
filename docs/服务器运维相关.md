# Shining ACG 运维架构与部署交接文档

## 1. 架构总览
由于当前服务器资源限制（**仅有 1 个公网 IP，且仅开放了 61080 端口**），系统采用了**单机容器化 + Nginx 前缀路由隔离**的设计方案。

### 1.1 流量流转路径
所有外网请求的流转路径如下：
`用户请求` -> `服务器公网IP:61080` -> (端口映射) -> `本地 8080 端口 (Nginx Gateway)` -> `分发至具体容器 (Dev/Prod)`

### 1.2 环境域名划分
基于同一端口，Nginx 根据访问的域名将请求路由到不同的隔离环境：
*   **生产环境 (Prod):** `api.shiningacg.club:61080` -> 路由至 `api-prod` 容器
*   **开发/测试环境 (Dev):** `test.api.shiningacg.club:61080` -> 路由至 `api-dev` 容器

---

## 2. 核心目录与数据持久化

服务器上的所有核心配置均放置在 `/opt` 目录下：

```text
/opt/
├── nginx_gateway/     # 全局 Nginx 网关配置与 docker-compose
│   └── conf.d/
│       └── shining.conf # 核心路由转发规则存放处
├── shiningacg_dev/    # 开发环境 Docker Compose、配置及环境参数
├── shiningacg_prod/   # 生产环境 Docker Compose、配置及环境参数 (与 dev 结构类似)
└── ssl/               # 存放 acme.sh 生成的 SSL 证书
```

**数据持久化目录：**
所有容器的有状态数据均挂载在外部磁盘（通过 `local` driver bind），以防误删容器导致数据丢失：
*   Dev 数据存放于：`/mnt/storage/shining_dev/` (包含 `postgres_data`, `minio_data`, `loki_data`, `grafana_data`)
*   *(Prod 数据存放于对应的 prod 目录下)*

---

## 3. 隔离设计详解 (Dev vs Prod)

为了在同一台机器上运行两套完全一致的服务而不冲突，我们在 Docker Compose 中做了以下隔离设计：

1.  **容器命名隔离：** 所有服务名均带有后缀，如 `api-dev` vs `api-prod`。
2.  **网络隔离：**
    *   `shining_network`: **全局外部网络**。只有需要被 Nginx 代理的服务（API、MinIO、Grafana）才加入此网络。
    *   `dev_internal` / `prod_internal`: **环境内部网络**。数据库 (Postgres) 等后端组件仅在此网络内，Nginx 无法直接访问，保证数据安全。
3.  **宿主机端口隔离：**
    为了方便直连调试，Dev 环境映射了一些非标准端口至宿主机（Prod 环境通常不映射）：
    *   Postgres-Dev: `15433` (对应容器内 5432)
    *   MinIO-Dev API: `19000` / 控制台: `19001`
    *   Grafana-Dev: `13000`

## 4. Nginx 网关与证书 (⚠️ 注意事项)

### 4.1 Nginx 代理规则 (`/opt/nginx_gateway/conf.d/shining.conf`)
Nginx 承担了 API 转发、对象存储代理和日志面板的路由：
*   `/` -> 转发给后端 Go API (`http://api-dev:8000`)
*   `/shining-bucket/` -> 转发给 MinIO 对象存储 (`http://minio-dev:9000`)
*   `/logs/` -> 转发给 Grafana 日志面板 (`http://grafana-dev:3000`，通过 rewrite 剥离前缀)

### 4.2 SSL 证书与泛域名改造说明（接手人必看）
当前 SSL 证书是通过 `acme.sh` 从 ZeroSSL 申请的单域名证书：
*   `api.shiningacg.club`
*   `test.api.shiningacg.club`

**🚨 后续改造建议：**
听说项目很快会申请**泛域名证书 (`*.api.shiningacg.club`)**。拿到泛域名证书后，请修改 Nginx 配置：
1. 取消现在的两个独立证书文件 (`fullchain_dev.pem` 和 `fullchain.pem`)。
2. 在 Nginx 的 server 块中统一使用该泛域名证书，以减少后期维护多个证书续签的麻烦。

## 5. 服务组件清单 (以 Dev 为例)

通过 `docker-compose.yml` 编排，单环境包含以下组件：
1.  **api-dev (Go Monolith):** 后端主程序。从 GHCR 拉取镜像，依赖 DB 和 MinIO 启动。
2.  **postgres-dev (PostgreSQL 17):** 关系型数据库，配置了基于 `pg_isready` 的健康检查。
3.  **minio-dev (MinIO):** 对象存储，存储用户上传的媒体文件，通过 `OSS_SERVER_URL` 向外网暴露服务。
4.  **日志监控三剑客：**
    *   `promtail-dev`: 挂载宿主机 Docker Socket，实时采集所有容器的标准输出日志。
    *   `loki-dev`: 接收、存储并索引日志（保留 31 天）。
    *   `grafana-dev`: 提供可视化界面，直接通过 Nginx 的 `/logs/` 路径访问。

## 6. CI/CD 自动化流水线 (GitHub Actions)

项目已配置完全自动化的 CI/CD，开发人员**无需手动登录服务器发版**。

*   **触发路径文件识别：** 只有修改了 `packages/server/**` 才会触发后端发版。
*   **开发环境部署 (Develop 分支)：**
    *   当代码 Push 到 `develop` 分支时，触发构建。
    *   构建带有 `:develop` 标签的 Docker 镜像并推送到 GHCR。
    *   **自动通过 SSH 登录服务器**，执行 `docker compose pull api-dev && docker compose up -d` 完成 Dev 环境无感重启。
*   **生产环境部署 (Git Tags 打标)：**
    *   当仓库推送 `v*` 开头的 Tag（例如 `v1.0.0`）时，触发构建。
    *   构建带有 `:latest` 和对应版本号的镜像推送到 GHCR。
    *   自动登录服务器 Prod 目录，拉取新镜像并重启 Prod 容器，期间带有健康检查。
    *   **注意：你需要提前在服务器 Prod 文件夹内放置需要的服务配置和最新的 Docker Compose 配置，也可以修改ci.yml来自动化**

## 7. 常用运维指令速查（Cheat Sheet）

如果你需要手动排查问题，请通过 SSH 登录服务器执行以下命令：

**1. 查看服务运行状态：**
```bash
cd /opt/shiningacg_dev   # 或 cd /opt/shiningacg_prod
docker compose ps
```

**2. 查看服务日志 (排查 Bug 首选)：**
```bash
# 查看后端 API 的实时日志，保留最后 100 行
docker compose logs -f --tail=100 api-dev

# 查看数据库日志
docker compose logs -f postgres-dev
```

**3. 重启单个服务：**
```bash
docker compose restart api-dev
```

**4. 证书手动更新 (正常情况下 acme.sh 会由 crontab 自动续签)：**
```bash
acme.sh --cron --home ~/.acme.sh
# 续签后重启 Nginx 使证书生效
cd /opt/nginx_gateway
docker compose restart
```

**5. 手动更新 API 镜像配置：**
修改 `/opt/shiningacg_dev/config.yaml` 或 `.env` 后，运行：
```bash
docker compose up -d
```
*(Docker Compose 会自动检测变更并仅重建受影响的容器)*
