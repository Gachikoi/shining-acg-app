# 前端工程师看后端（速览）

> 给前端同学的通俗说明：仓库怎么拆、后端在哪、接口从哪来、数据库在哪、你怎么接 API。  
> 更细的后端说明书见 [`packages/server/README.md`](../packages/server/README.md)。  
> 用首页帖子 Feed 走通整条请求链路的例子见 [`首页Feed请求链路详解.md`](./首页Feed请求链路详解.md)。

---

## 1. 一句话理解整个项目

这是一个 **单体仓库（monorepo）**：

| 目录 | 你是谁时关心什么 |
|------|------------------|
| `packages/web` | **前端**：SvelteKit，日常开发主战场 |
| `packages/server` | **后端**：Go 服务，接口与数据库都在这 |
| `packages/android` / `ios` / `harmonyos` | 各端壳，一般可先忽略 |
| `scripts/` | 仓库级工具（含生成前端 API 客户端） |
| `docs/` | 需求 Spec、设计稿、运维说明等 |

浏览器里的页面跑在 **web**；点赞、登录、发帖等数据请求打到 **server**；真正存数据的是 **PostgreSQL**（本地常用 Docker 起）。

```text
浏览器 (web :5173)
    │  HTTPS / 代理
    ▼
Go 后端 (server :8000)  ──►  PostgreSQL
                        ──►  MinIO（图片/视频等文件）
```

---

## 2. 后端是什么技术？文件大概在哪？

- **语言**：Go  
- **入口**：`packages/server/cmd/main.go`（本地一般 `go run ./cmd`，监听 **8000**）  
- **接口风格**：用 **Protobuf** 定义服务，经 **Connect-Go** 对外；对前端来说主要是 **REST 风格路径**（如 `/v1/users/me`），不是手写一堆 Express 路由文件。  
- **分层（了解即可）**：

```text
proto（接口合同）
  → service（接请求）
  → biz（业务逻辑）
  → repo（读写库）
  → model（表结构 / GORM）
```

配置：`packages/server/config.yaml`（数据库账号、端口等）。

---

## 3. 数据库在哪里？

| 问题 | 答案 |
|------|------|
| 用什么库？ | **PostgreSQL 17** |
| 本地怎么起？ | `cd packages/server && docker compose up -d` |
| 本机连哪个端口？ | 宿主机 **5433** → 容器内 5432（避免和本机已有 Postgres 抢 5432） |
| 账号/库名在哪看？ | `packages/server/config.yaml` 的 `db`，或环境变量 `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` |
| 表怎么建？ | 开发期主要靠 GORM **AutoMigrate**（在 `packages/server/internal/repo/db.go`），**没有**单独一大套 `migrations/` 给你改 |
| 文件存在哪？ | 图片等走 **MinIO**（S3 兼容），不是塞进 Postgres 里 |

**前端一般不直连数据库**，只通过后端 HTTP API 读写。

更偏设计的说明：`packages/server/doc/Database-Design.md`。

## 4. 「有哪些接口？」去哪看

接口的**合同**写在：

```text
packages/server/proto/api/
```

大致业务块（按目录理解即可）：

| 区域 | Proto 位置（示意） | 常见用途 |
|------|-------------------|----------|
| 登录鉴权 | `main/auth/` | 登录、Token |
| 用户 | `main/user/` | 资料、`/v1/users/me` 一类 |
| 帖子 / Feed | `main/post/`、`main/feed/` | 发帖、信息流 |
| 评论 | `main/comment/` | 评论 |
| 通知 | `main/notification/` | 通知列表等（与通知中心 Spec 相关） |
| 媒体 | `media/` | 上传相关 |
| 举报 / 审核 / 分区 / 部门 / 同步 / 实时 | 各自 `main/...` | 按产品需要再深入 |

生成后的 **OpenAPI / Swagger** 在前端包里：

```text
packages/web/swagger.swagger.json
```

用编辑器打开，或导入 Postman / Apifox，能看到路径、请求体、响应类型。

生成后的 **TypeScript 客户端**（你真正 import 的）：

```text
packages/web/src/lib/api/
```

例如：`import { userServiceGetMe } from '$lib/api'`（具体函数名以生成为准）。

> 注意：Swagger 里「有定义」≠ 本地后端一定已经实现并注册。不确定是否可用时，问后端或看 `packages/server/cmd/app.go` 里实际挂了哪些服务。

## 5. 前端怎么接接口？（你每天用的方式）

### 5.1 日常调用

1. 在 `packages/web` 里写页面 / store。  
2. 从 `$lib/api` 引入生成好的函数。  
3. **不要手改** `packages/web/src/lib/api/**`（会被重新生成覆盖；仓库规则也禁止手改）。

请求基址与域名在：

- `packages/web/src/lib/constants.ts` → `DOMAIN_CONFIG.api`  
  - 测试：`test-api.shiningacg.club`  
  - 正式：`api.shiningacg.club`  
- Axios / Token：`packages/web/src/hey-api.svelte.ts`（`Authorization: Bearer`，token 在 `localStorage`）

本地调试常用 **Whistle** 把 API 域名指到本机 `127.0.0.1:8000`（见 `packages/web/README.md`）。

### 5.2 协议变了怎么办？

后端改了 `.proto` 之后，在**仓库根目录**执行：

```bash
deno task gen:api
```

它会大致：

1. 用 Buf 从 proto 生成 / 更新 `packages/web/swagger.swagger.json`  
2. 用 OpenAPI 生成器刷新 `packages/web/src/lib/api/**`

然后你改页面去用新函数即可。

## 6. 「怎么写接口？」——分你是前端还是要动后端

### 只做前端

通常 **不写后端接口**，只：

1. 确认 Swagger / `$lib/api` 里有没有目标接口；  
2. 没有 → 找后端加 proto + 实现；  
3. 有 → `gen:api`（若本地 swagger 旧了）→ 在页面里调用。

### 你要自己加一个后端接口（前后端一起改）

简化步骤：

1. **改合同**：在 `packages/server/proto/api/...` 增加/修改 service 方法，并配上 HTTP 注解（`google.api.http`，路径形如 `/v1/...`）。  
2. **生成代码**：在 `packages/server/proto` 下按 README 跑 `buf generate`。  
3. **写实现**：`internal/service` 接请求 → `biz` 逻辑 → `repo`/`model` 访问库。  
4. **注册服务**：挂到 `cmd/app.go`，Wire 注入更新后跑 `wire`。  
5. **表结构**：改 GORM model，并纳入 AutoMigrate（如需要）。  
6. **给前端**：仓库根 `deno task gen:api`，再在 web 里调用新方法。

前端同学若只改到第 1、6 步，中间实现务必和后端同学对齐。

## 7. 本地怎么把前后端跑起来（最小集）

```bash
# 1）数据库等基础设施
cd packages/server
docker compose up -d

# 2）后端
go mod tidy
go run ./cmd          # :8000

# 3）前端（另开终端）
cd packages/web
cp .env.example .env.local   # 按需；常用 PUBLIC_IS_TEST=true
deno task gen:api            # 协议有变再跑
deno task dev                # :5173
```

再用代理把 `*api.shiningacg.club` 指到 `127.0.0.1:8000`。

## 8. 和「通知中心 Spec」的关系（避免混淆）

`.specs/notification/...` 里的 Spec 主要描述 **前端页面与交互**（Tab、未读、Mock 等）。  
本期通知 IM 很多能力仍是 **前端 Mock / 本地状态**；真实通知 API 在 proto 的 `notification` 服务里预留，对接时仍走「proto → gen:api → `$lib/api`」，**不要**在前端臆造或手改生成客户端。

## 9. 常用路径速查

| 你想… | 打开 |
|------|------|
| 看有哪些 HTTP 接口 | `packages/web/swagger.swagger.json` |
| 在代码里调接口 | `packages/web/src/lib/api/` |
| 改请求 Token / Axios | `packages/web/src/hey-api.svelte.ts` |
| 看 API 域名 | `packages/web/src/lib/constants.ts` |
| 改/加接口定义 | `packages/server/proto/api/` |
| 起数据库 | `packages/server/docker-compose.yml` |
| 数据库账号配置 | `packages/server/config.yaml` |
| 重新生成前端客户端 | 仓库根：`deno task gen:api` |
| 后端总览 | `packages/server/README.md` |

---

## 10. 三条铁律（前端）

1. **`$lib/api` 只引用、不手改**；协议变了跑 `deno task gen:api`。  
2. **不直连 Postgres**；数据一律走后端 API。  
3. **Swagger 有定义 ≠ 本地一定能调通**；以后端是否实现并注册为准。
